# 防跌倒人体检测项目开发日志

> 记录项目从零到可用的完整开发过程，按时间线整理方案设计、实验测试、问题排查与版本迭代。
> 依据项目内代码、git 提交、模型指标与数据产物整理，记录均为实际发生的工作内容。

---

## 项目概述

- **目标**：基于视频的人体跌倒检测与分级预警（正常 / 失衡 / 摔倒），并支撑 Web/移动端实时监控。
- **技术路线**：视频帧 → RTMDet 人体检测 → RTMPose 骨架关键点提取（17 点 COCO）→ 滑动窗口时序建模（TCN / ST-GCN）→ 状态机四级预警（SAFE / LOW / HIGH / IMMEDIATE）。
- **核心产物**：
  - 数据流水线：关键点提取、交互式标注、标签转换、FPS 统一重采样
  - 模型训练/推理：`train.py`、`search.py`（超参搜索）、`eval_model.py`、`fast_infer.py`
  - 实时服务：`demo_live.py`（本地实时推理）→ `server.py` / `CareWatch-Backend-main`（HTTP/WS 服务）
- **环境**：`openmmlab` conda 环境（PyTorch 2.0.1 + cu118、mmcv 2.1.0、RTX 4070 Laptop），mmpose 源码开发模式。

## 阶段 0：环境搭建与方案设计（~2026-08-04）

### 关键节点
- 搭建 `openmmlab` conda 环境，安装 PyTorch 2.0.1（CUDA 11.8）+ mmcv 2.1.0 + mmdet + mmpose，mmpose 以源码开发模式挂载在工作区，便于追踪模型层行为。
- 调研公开跌倒数据集，确定第一轮仅用 3 个符合「视频 → 骨架 → 时序分类」路线的数据集：
  - **URFD**（30 段跌倒 + 40 段 ADL，有序列级标签，需补标阶段）
  - **CAUCAFall**（家庭非受控环境，5 类跌倒 + 5 类日常，需补标）
  - **FallVision**（自带每帧 17 点骨架 CSV，仅抽样补标）
  - 传感器类数据集（SisFall / UniMiB / KFall 等）排除出视觉主训练路线；KFall 仅参考其时间点定义。
- 约定 4 个关键时间点标注定义：`risk_start_frame`（失衡开始）/ `fall_start_frame`（不可恢复下坠）/ `impact_frame`（首次触地）/ `stable_fallen_frame`（倒地稳定）。

### 技术选型
- 检测：RTMDet（小模型、速度快），姿态：RTMPose-m（256x192）。
- 时序模型：**TCN**（~38 万参数，因果膨胀卷积，实时性好）与 **ST-GCN**（~100 万参数，空间图卷积理解骨架结构）双路线对比。

## 阶段 5：推理性能优化 fast_infer（2026-08-24 ~ 08-25）

### 关键节点
- 08-25 完成 `fast_infer.py`：绕开 mmdet/mmpose 高层 `test_step` / `predict` 的 Python 后处理包装，只保留模型前向（`mode='tensor'`）+ 手写紧凑后处理：
  - **检测**：`cls_scores / bbox_preds` → `filter_scores_and_topk` → 解码 → NMS。参数收紧（`nms_pre=1000`、`score_thr=0.3`、`max_per_img=100`、`iou_thr=0.65`）。
  - **姿态**：`pose_model(inputs, ds, mode='tensor')` 拿 simcc → `head.decode` → 坐标还原，与 mmpose 模型层 `add_pred_to_datasample` 逐字一致（`kpts / input_size * bbox_scales + bbox_centers - 0.5*bbox_scales`，分母用 192/256 不减 1）。

### 实验测试
- 耗时对比：检测 **185ms → ~46ms**，姿态 **~44ms → ~32ms**。
- `compare_fast.py` 一致性回归：fast 管线 vs 低层 API 对齐，bbox < 3px、kpts < 5px → PASS。
- 遗留说明：关键点仍差 ~3.6px，来自旧链路 `predict` 里的 flip_test（TTA）双前向融合，fast 改为单次前向（与训练一致）；960x540 上约 0.3%，阈值 5px 可忽略。

### 问题排查与解决
- **检测 2K 大图慢**（1440x2560 每帧约 1.7s）：用 `--detect_every 5` 复用 bbox，或 `--infer_width` 缩放输入。

## 阶段 7：数据统一与 FPS 对齐（2026-08-26）

### 关键节点
- **FPS 统一约定**：npy 只存 `(N, 17, 3)` 关键点坐标，不含 FPS 元数据；FPS 只体现在帧数 N 上。
- `resample_labels.py`（扩展含 `resample_keypoints`）：混合 25/30fps 源按浮点比例时间重采样统一到 **15fps**；关键点取区间起点帧（不插值避免伪姿态）、标签取区间内最高等级；同一时间网格保证对齐；先 `--dry_run` 预览再覆盖写盘。
- `demo_live.py` 增加 `--infer_fps 15` 时间采样匹配训练（固定步进采样点，源 25/30/16fps 都精确到 ~15fps）。
- **训练/推理一致参数**：`window=30 @ 15fps ≈ 2 秒`（`train.py` 默认 window=30 无需改）。
- `make_labels_from_xlsx.py`：从标注 xlsx（起始帧 + 状态分段）生成帧级 `labels.npy`，支持多标注文件批量转换。

### 实验测试（标签策略）
- 对比整窗 max 与「窗口尾部 max」两种标签策略：
  - 整窗 max 会把「跌倒前整段正常姿态」提前污染为异常，导致报警提前、假阳性升高。
  - 最终采用 **label_tail（方案 2）**：窗口标签只看最后 `window//3` 帧的最高等级，让标签反映窗口尾部真实状态，报警更即时。

### 问题排查与解决（重大 Bug）
- **demo_live 时间采样死循环**：`last_sample_t` 初始化为 `0`，与绝对时间戳（~1.7e9）比较 → `while` 死循环约 260 亿次，卡在 imshow 之前、窗口不弹出。
  - 症状特征：完整模式打印「视频源」后卡死无窗口，但 `--play_only` 正常（它走 continue 跳过采样逻辑）。
  - 修复：`last_sample_t` 初始化为 `time.time() - sample_interval`。
  - 经验：RTMP 流本身正常时 demo_live 卡住先怀疑自己的代码，用 `-u` 无缓冲或 kill 后看输出定位。

## 阶段 8：状态机调参与最终模型（2026-08-26）

### 关键节点
- `state_machine.py`：阈值 / 连续确认次数全部参数化（low/high/imm thresh + count），支持 2 分类分数、3 分类概率、类别整数三种输入。
- **防误报调参**：原 IMMEDIATE 单次 >0.85 误报多，放宽为**连续确认**：
  - LOW_RISK：P1 > 0.60 连续 3 次
  - HIGH_RISK：P1 > 0.75 连续 2 次
  - IMMEDIATE：P2 > 0.85 连续 5 次
- `features.py` 增强特征 `enhance_keypoints`（方案 B）：3 通道 → **9 通道**
  - 0-2 原始 x,y,conf；3-4 速度 vx,vy；5 关节相对重心角度；6 到重心距离；7 关节弯曲角；8 躯干倾角（广播，跌倒时躯干由直立转水平）。
- `search.py`：网格搜索 + 动态调参，按 `score = avgF12 - fp_penalty * fp_rate`（兼顾不稳/摔倒精确率并惩罚误报）选最优超参后重训。
- 08-26 23:17 训练最终 `checkpoints/best_model.pt`（in_ch=9，3 分类）。

### 实验测试（最终模型评估，`best_model.metrics.json`）
| 指标 | 值 |
|------|-----|
| Accuracy | 0.873 |
| Macro F1 | 0.820 |
| avg F1(失衡+摔倒) | 0.774 |
| 误报率 fp_rate | 0.304 |
| score | 0.622 |

| 类别 | Precision | Recall | F1 | TP | FP | FN |
|------|-----------|--------|-----|-----|-----|-----|
| 0 正常 | 0.986 | 0.846 | 0.910 | 2447 | 36 | 447 |
| 1 失衡 | 0.866 | 0.923 | 0.894 | 743 | 115 | 62 |
| 2 摔倒 | 0.491 | 0.986 | 0.655 | 350 | 363 | 5 |

- 结论：摔倒类召回极高（0.986，漏检仅 5 帧）符合「宁可误报不可漏报」的目标；正常类误报率低；失衡类 F1 0.894。摔倒类误报（FP 363）主要由失衡/正常被误判为摔倒导致，后续通过状态机连续确认压制。

## 常见问题与踩坑记录（汇总）

| 现象 | 根因 | 解决 |
|------|------|------|
| RTMP H.265 流打不开 | OpenCV 无 HEVC 解码 | imageio-ffmpeg relay 转码 H.264 再读 |
| demo_live 打印视频源后卡死无窗口 | `last_sample_t=0` 与绝对时间戳比较触发 while 死循环 | 初始化为 `time.time() - interval` |
| 训练/推理效果对不上 | 训练 25/30fps、推理不同步 | 统一时间重采样到 15fps + window=30 |
| 整窗 max 标签导致报警提前 | 正常帧被窗口内未来跌倒污染 | 改用窗口尾部 label_tail 帧 max |
| IMMEDIATE 单帧误报多 | 阈值只判单次 | 改为连续 5 次 >0.85 确认 |
| 关键点坐标差 ~3.6px | 旧链路 flip_test TTA 双前向 | fast 单前向（与训练一致），阈值 5px 容忍 |
| 2K 大图检测慢（1.7s/帧） | RTMDet 处理大图开销大 | `--detect_every 5` 复用 bbox / `--infer_width` 缩放 |
| VS Code 报 mmpose/mmdet import 错误 | 默认解释器非 openmmlab 环境 | 忽略误报，实际运行用 openmmlab 解释器 |
| 自动化终端含 `&`/`$env:` 命令异常 | 终端 ^U 注入问题 | 用无引号直接路径或 TestClient 脚本 |
